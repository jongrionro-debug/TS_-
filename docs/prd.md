- 문서 작성일: 2026-10-22
- 최종 수정일: 2026-10-23
- 문서 상태: 기본 EDA 완료, 첫 모델 실험의 데이터 처리·입력 구성 확정 — 모델 구현·성능 검증 예정

## 1. 프로젝트 개요

### 1.1 연구 질문

> 대화형 서비스에서, 과거 요청량·토큰량에 최근 대화 상태 정보를 추가하면 다음 10분의 입력·출력 토큰 수요를 더 잘 예측할 수 있는가?

매 1분 경계에서 당시까지 관측 가능한 정보를 사용해, 다음 10분 동안 도착할 대화형 요청들의 입력 토큰 합과 최종 출력 토큰 합을 각각 예측한다. 집계 이력만 사용하는 기준 모델에 활동 대화 수와 대화 상태 요약을 단계적으로 추가하여, 각 정보 묶음의 추가 예측가치를 평가한다.

> **목표 해석 확인 (2026-10-22):** 이 문서와 비교한 5분 초안은 모두 요청 도착 기준이다. 예측 구간에 도착한 요청의 최종 출력 전체를 정답에 포함하며, 구간 내 실제 생성량을 뜻하지 않는다. 대화 중 검토한 실제 생성량·응답시간 균등 배분은 별도 대안이며 채택하지 않았다. 기존 도착 기준 EDA를 이 이유로 무효화하거나 재계산할 필요는 없다. [대안 검토와 해석 정정](../eda/results/target_definition_review/audit.json)을 참고한다.

10분 지평은 운영 준비 시간을 확보하려는 목적과 관측된 후속 요청 간격의 5·10·15분 비교를 함께 고려한 설계 선택이다(§6.1). 특정 지평이 최적이거나 예측 성능이 우월하다고 검증된 것은 아니다. 매 시점의 정답은 한 쌍의 10분 누적값이며, t+600의 단일 시점 토큰량이나 1분 단위 토큰량 10개를 각각 예측하는 문제가 아니다.

핵심 기여 후보는 새로운 예측 알고리즘이 아니라 **집계 이력에 대화 연결 정보를 추가하는 것이 유용한지 공정한 비교로 확인하는 것**이다. 성능 향상은 아직 검증되지 않았으며, 개선이 없거나 특정 조건에서만 나타나는 결과도 보고한다.

### 1.2 문제의 중요성

동일한 요청 수라도 요청당 입력·출력 길이에 따라 토큰량이 달라진다. 또한 동일한 최근 토큰량이 소수 대화에 집중됐는지, 여러 대화에 분산됐는지에 따라 후속 요청의 발생과 길이 구성이 다를 가능성이 있다.

단기 토큰 수요 예측은 서비스 용량 계획을 위한 기초 정보가 될 수 있다. 다만 이 프로젝트는 토큰 예측 정확도를 평가하며, 실제 GPU 이용률·처리량·비용 절감·SLO 개선을 입증하지 않는다.

### 1.3 현재 설계에서 고정하는 사항

| 항목 | 결정 |
|---|---|
| 주 분석 대상 | `Log Type == "Conversation log"`인 요청 |
| 예측 시점 간격 | 원본 Timestamp의 60초 경계마다 1회 |
| 예측 대상 구간 | `[t, t + 600초)` |
| 모델 출력 | 다음 10분 누적 입력 토큰, 다음 10분 도착 요청의 최종 출력 토큰 |
| 모델 구성 | 입력·출력 각각 별도의 XGBoost 회귀 모델 |
| 핵심 비교 | A: 집계 이력 → B: 활동 대화 수 추가 → C: 대화 상태 추가 |
| 입력 형태 | 매 1분 예측 시점마다 과거 로그를 요약한 숫자 한 행; 프롬프트 원문이나 Session ID 자체는 넣지 않음 |
| 0토큰 기록 | 기본 실험에서 유지하고 최근 15분 입력 토큰 0인 요청 수를 A/B/C에 공통 제공 |
| 평가 원칙 | 시간순 분할, 동일 예측 시점, 동일 튜닝 예산, 관측 시점 준수 |

현재 정답은 **누적 토큰 두 값**이다. 매 1분 경계마다 하나의 10분 누적값 쌍을 예측하며, t+600의 단일 시점 값이나 `[t,t+60)`, `[t+60,t+120)`, …, `[t+540,t+600)`의 10개 분별 토큰량을 각각 예측하는 다중 지평 문제와 구분한다.

기존 기획의 ‘배경 수요 + 세션별 후속 수요 합산’은 이번 기본 구현에 포함하지 않는다. Session ID별 독립 모델도 만들지 않는다. 대화별 상태를 계산한 뒤 전체 대화형 서비스의 설명변수로 요약한다.

첫 실험은 §4의 입력 목록으로 시작한다. 최종 채택 모델은 입력·출력 각각의 검증 성능으로 정한다. 입력 예측에는 C, 출력 예측에는 A가 선택되는 결과도 허용하며, C가 가장 좋다고 미리 가정하지 않는다.

### 2.3 주요 필드

| 필드 | 의미 | 분석상 주의점 |
|---|---|---|
| `Timestamp` | 기준 첫날 자정 이후 요청 제출까지의 상대 초 | Unix timestamp로 변환하지 않음 |
| `Session ID` | 대화 식별자 | 문자열로 유지. 사용자 ID가 아님 |
| `Elapsed time` | 제출부터 최종 응답 완료까지의 초 | TTFT나 GPU 계산시간으로 해석하지 않음 |
| `Model` | 요청 모델 | 최근 15분 GPT-4 요청 비율을 A/B/C에 공통 제공; 한 대화에서 모델이 바뀔 수 있음 |
| `Request tokens` | 요청 입력 길이 | 도착 시점에 이용 가능한 정보로 가정 |
| `Response tokens` | 최종 응답 길이 | 응답 완료 이후에 이용 가능 |
| `Total tokens` | 입력·출력 길이 합 | 입력·출력 정합성 점검에 사용 |
| `Log Type` | API 또는 대화형 호출 방식 | 주 실험은 대화형으로 제한 |

공개 스키마에는 원문, 주제, 언어, 임베딩, 사용자 속성, 서버 사용률이 없다. 토큰 길이를 의미 정보의 직접 측정값으로 해석하지 않는다.

### 2.4 시간 해석

관리자 답변에 따르면 시간대는 UTC+8이며 서머타임은 없다. 기준 달력 날짜는 확인되지 않았다. [관리자 답변](https://github.com/HPMLL/BurstGPT/issues/9)

- 하루 중 시각은 원본 `Timestamp % 86400`으로 계산한다.
- 최소 Timestamp를 뺀 경과시간은 시각화에 사용하되, 하루 중 시각과 혼용하지 않는다.
- 실제 날짜·월요일·주말·공휴일을 임의로 부여하지 않는다.
- 24시간·7일 반복은 상대시간으로 탐색할 수 있다. 7일 순환위상과 실제 요일명은 구분한다.

## 3. 예측 문제와 정보 이용 시점

### 3.1 목표값

대화형 요청 i의 도착시각을 a_i, 입력 토큰을 x_i, 최종 출력 토큰을 r_i라고 한다.

```text
Y_input(t)  = sum(x_i for requests with t <= a_i < t + 600)
Y_output(t) = sum(r_i for requests with t <= a_i < t + 600)
```

두 값 모두 요청 도착 시각을 기준으로 묶는다. 출력 합계에는 t+600 이후에 생성된 출력도 포함될 수 있다. 따라서 ‘그 10분 동안 실제 생성된 토큰량’이 아니다. 매 1분 경계의 10분 구간은 서로 9분씩 겹치지만, 각 시점의 정답은 하나의 누적 입력·출력 토큰 쌍이다.

출력 0 요청은 기본적으로 유지한다. 현재 대화형 데이터에서는 출력이 0인 1,856건 모두 입력·합계 토큰도 0이다. 이 기록은 토큰 합계에는 기여하지 않지만 요청 수와 대화 상태에는 영향을 주므로, §5.1에 따라 유지하고 별도로 구분한다. 출력 목표는 **기록된 실제 출력량**이며 실패가 없었다면 발생했을 잠재 출력 수요가 아니다. 0토큰 기록의 원인을 CSV만으로 특정하지 않는다.

미래에 처음 등장하는 대화와 상태 추적 대상 밖의 대화도 목표값에 포함한다. 상태를 계산할 수 있는 대화의 후속 요청만 정답으로 고르면 연구 대상이 바뀐다.

### 3.2 요청 도착과 응답 완료의 구분

요청 완료시각은 `c_i = Timestamp_i + Elapsed time_i`로 구성한다. 이를 사용하기 전에 Elapsed time의 자료형·결측·음수·극단값과 완료시각 정합성을 점검한다.

| 정보 | 예측 시점 t에서의 사용 조건 |
|---|---|
| 요청 시각·입력 길이·대화 ID·모델 | `a_i < t` |
| 최종 출력 길이·최종 응답시간 | `c_i < t` |
| 미래 도착 요청의 정보 | 입력 특징에는 사용하지 않음 |
| 미래 토큰 합계 | 사후 정답 계산에만 사용 |

기본 설계는 요청 도착 정보가 지연 없이 관측 가능하다고 가정한다. 실제 로그 수집 지연은 공개 CSV로 확인할 수 없으므로 보고서에 가정을 명시한다.

쉽게 말해 **질문의 길이는 질문이 들어오면 알 수 있지만, 최종 답변 길이는 답변이 끝나야 알 수 있다**는 규칙이다. 예를 들어 11:59에 입력 100토큰인 요청이 도착하고 12:01에 출력 200토큰으로 완료됐다면, 12:00 예측에는 입력 100을 사용할 수 있지만 출력 200은 사용할 수 없다. 최종 CSV에 출력 200이 적혀 있어도 12:00 당시 이미 알고 있었다고 처리하지 않는다.

같은 이유로, 요청 도착 직후의 0토큰 여부는 **`Request tokens == 0`만으로 표시**한다. 아직 끝나지 않은 응답의 `Response tokens`나 `Total tokens`를 확인해 요청을 분류하지 않는다. ‘입력·출력 모두 0’이라는 판정은 사후 EDA에서 확인한 사실이며, 도착 시점의 입력 특징 정의와 구분한다.

### 3.3 과거 출력 특징의 정의

주 실험 A/B/C에는 **완료시각 기준 출력 이력**을 동일하게 제공한다.

```text
completed_output_last_5min(t)
    = sum(Response tokens for requests with t-300 <= c_i < t)
```

이는 완료된 요청의 전체 출력량을 완료시점에 기록하는 통계이며 순간 GPU 생성률이 아니다. 도착 기준 목표 `Y_output`과 별도로 이름 붙인다.

이번 EDA에서는 완료시각을 계산할 수 있었으므로 이 특징을 유지한다. 응답시간이 0초라는 이유만으로 완료 정보를 삭제하지 않는다. 현재 기록의 정밀도 한계는 보고서에 명시한다.

완료시각 품질 문제로 이 특징을 구성할 수 없다면 임의로 채우지 않는다. 전체 비교에서 공통으로 제외하고 연구 질문을 ‘과거 요청량·입력 토큰량 대비’로 조정한다. 이 변경은 실험 설정에 기록한다.

### 3.4 학습 정답의 확정 시점

모델 학습·재학습 시각을 T라고 할 때 입력 정답은 해당 10분 구간이 끝난 표본만 사용한다. 출력 정답은 구간이 끝나고 그 안의 요청들이 모두 완료된 표본만 사용한다.

```text
입력 학습 가능: t + 600 <= T
출력 학습 가능: t + 600 <= T AND 해당 구간 모든 요청의 c_i < T
```

빈 구간도 종료 전에는 0으로 확정할 수 없다. 최종 CSV에 값이 있다는 이유만으로 학습 시점에 이미 알았다고 가정하지 않는다. 학습·검증 경계에 10분만 비우는 방식은 오래 걸린 응답의 정답 누출까지 보장하지 않는다.

## 4. 연구 가설과 비교 실험

### 4.1 가설

| 가설 | 내용 | 비교 |
|---|---|---|
| H1 | 최근 활동 대화 수가 집계 수요 이력에 추가 예측가치를 제공한다. | B 대 A |
| H2 | 대화 상태 요약이 활동 대화 수를 넘어 추가 예측가치를 제공한다. | C 대 B |
| H3 | 대화 정보의 전체 추가 효과는 입력·출력 목표에서 다르게 나타날 수 있다. | C 대 A를 목표별로 평가 |

이는 예측 가설이며 인과 가설이 아니다. 대화 정보가 수요를 발생시키는 원인임을 증명하지 않는다. 입력에서만 개선되면 입력에 대한 근거로 보고한다. 가설이 지지되지 않는 결과도 유지한다.

### 4.2 특징 묶음

| 모델 | 특징 구성 |
|---|---|
| A: 집계 기준 모델 | 과거 요청 수·입력 토큰 합·완료 기준 출력 토큰 합의 지연값·합계·변동성, 입력 길이 분포, 하루 중 시각, 모델 구성비, 입력 0 요청 수 |
| B: 활동 대화 추가 | A + 최근 5·15·30분의 고유 유효 Session ID 수 |
| C: 대화 상태 추가 | B + 최근 30분 활동 대화들의 최근성·관측 요청 횟수·관측 연령·마지막 입력 길이·입력 길이 변화 요약 |

첫 비교 실험의 **A 공통 입력**은 다음 목록으로 고정한다. B/C에도 동일한 정의와 값으로 제공한다.

| 입력 | 첫 실험의 계산 규칙 |
|---|---|
| 최근 수요 이력 | 요청 수·입력 토큰 합·완료 기준 출력 토큰 합 각각에 대해 직전 1·2·3분 값 |
| 누적 수요 | 같은 세 통계 각각의 최근 5·15·30·60분 합계 |
| 수요 변동성 | 최근 15분의 분별 요청 수·입력량·완료 기준 출력량 각각의 표준편차 |
| 요청당 입력 길이 분포 | 최근 15분에 도착한 요청들의 입력 길이 평균·표준편차·중앙값·90분위수 |
| 시간대 | `t % 86400`으로 계산한 하루 중 시각; 실제 요일·주말·공휴일은 넣지 않음 |
| 모델 구성비 | 최근 15분 도착 요청 중 GPT-4 비율 |
| 입력 0 요청 수 | 최근 15분 도착 요청 중 `Request tokens == 0`인 요청 수 |

최근 W분 도착 정보는 `[t - W×60, t)`, 완료 기준 출력 정보는 같은 범위의 완료시각으로 계산한다. ‘직전 1·2·3분 값’은 각각 `[t-60, t)`, `[t-120, t-60)`, `[t-180, t-120)`의 값이다. 표준편차는 모집단 기준(`ddof=0`)으로 통일한다. 90분위수는 값의 90%가 그 이하인 경계값이며, 분위수 계산은 선형 보간으로 통일한다.

새로 도착한 요청이 없는 구간의 요청 수·입력 토큰 합·입력 0 요청 수는 0이다. **완료 기준 출력 합계는 별도로 집계한다. 새 요청이 없어도 이전에 도착한 요청의 응답이 그 구간에 끝나면 양수가 될 수 있으며, 완료된 요청도 없는 경우에만 0이다.** 완전한 15분 이력에서 어떤 통계의 분별 값이 모두 0이면 해당 통계의 변동성은 0이다. 요청당 입력 길이 분포와 모델 구성비는 도착 요청이 없으면 결측으로 둔다. 입력 길이 표준편차는 요청이 1건이면 0이다. 없는 요청의 평균 길이나 모델 비율을 임의로 0이라고 채우지 않는다.

B는 최근 5·15·30분 활동 대화 수만 추가하고, C는 §4.4의 기본 상태 요약만 추가한다. 모델 구성비와 0입력 요청 수를 C에만 제공하지 않는다. A/B/C의 중첩 관계를 유지해 대화 정보의 추가 효과를 비교한다.

첫 비교에서는 위 목록과 시간창을 고정한다. 변수 추가·축소 실험을 한다면 검증 구간에서만 선택하고 A/B/C의 공통 입력·평가 시점·튜닝 예산을 함께 맞춘다. 전체 EDA에서 상관이 높았다는 이유만으로 특정 시간창을 최적이라고 확정하지 않는다.

### 4.3 집계 기준 모델의 강도

A에도 ID 연결 없이 계산 가능한 최근 입력 길이 평균·표준편차·소수의 분위수 등을 제공한다. 그래야 C의 개선이 단순히 입력 길이 통계를 추가했기 때문인지 혼동하는 문제를 줄일 수 있다.

예를 들어 A의 ‘최근 모든 요청의 입력 길이 중앙값’과 C의 ‘각 활동 대화의 마지막 요청을 하나씩 골라 구한 입력 길이 중앙값’은 다르다. 후자는 대화 연결을 활용한 특징이다.

그래도 결론은 ‘설정한 집계 기준특징 대비 추가 가치’로 한정한다. 집계 정보로 표현할 수 있는 모든 예측 가능성을 배제했다는 의미는 아니다.

### 4.4 대화 상태의 정의

활동 대화는 실제 종료 여부와 무관하게 **최근 30분에 한 번 이상 요청이 관측된 대화**로 정의한다. Session ID는 모델에 그대로 인코딩하지 않고 연결키로 사용한다.

| 상태 | 계산 및 요약 예시 |
|---|---|
| 최근성 | t에서 마지막 과거 요청시각을 뺀 값; 활동 대화 전체의 중앙값·90분위수 |
| 관측 요청 횟수 | t 이전 파일 내 요청 수; 활동 대화 전체의 중앙값·관측 요청이 1회인 대화 비율 |
| 관측 연령 | t에서 파일 내 최초 과거 요청시각을 뺀 값; 활동 대화 전체의 중앙값 |
| 마지막 입력 길이 | 대화별 마지막 과거 요청의 입력 길이; 활동 대화 전체의 중앙값·90분위수 |
| 입력 길이 변화 | 과거 요청이 2개 이상인 대화의 마지막 입력 길이에서 그 직전 길이를 뺀 값; 중앙값·계산 가능한 대화 수 |

최근 30분은 **요약할 대화를 고르는 기준**이다. 각 대화의 관측 요청 횟수·관측 연령·마지막 두 입력 길이는 최근 30분으로 잘라 계산하지 않고, 파일 내에서 t 이전에 관측된 해당 대화의 이력으로 계산한다. 관측 연령은 파일 내 최초 관측 이후의 시간이며 실제 대화의 전체 지속시간을 뜻하지 않는다. 파일 이전 이력은 포함하지 않는다. 전체 CSV에서 얻은 최종 세션 길이·마지막 시각·미래 반복 여부는 입력으로 사용하지 않는다.

관측 연령은 첫 C 모델의 기본 특징에 포함한다. 대화 내 과거 요청 간격은 기본 비교 이후의 확장 특징으로 둔다. 기본 대화 상태 특징의 추가 예측가치는 A/B/C 비교 실험으로 평가하며, 이번 EDA만으로 성능 향상이 확인됐다고 해석하지 않는다.

활동 대화가 없으면 B의 활동 대화 수와 C의 변화량 계산 가능 대화 수는 0이다. 정의되지 않는 중앙값·분위수·1회 대화 비율은 결측으로 둔다. 활동 여부는 B의 최근 30분 대화 수로 구분하며, 실험별로 결측 행을 다르게 삭제하지 않는다.

## 5. 데이터 품질과 전처리 요구사항

1. 전체 대화형 표본을 사용한다. 무작위 요청 추출로 대화 연결을 끊지 않는다.
2. 대화형만의 최소·최대 시각, 일별 관측량, 긴 빈 구간을 점검한다.
3. Session ID의 결측·빈 문자열·공통 대체값 여부, 고유 ID 수와 반복 대화 비율을 확인한다.
4. ID 없는 요청도 기본 목표값에는 포함한다. 상태특징은 유효 ID에서 계산하고 ID 관측률을 보고한다. 결측 ID들을 하나의 대화로 합치지 않는다.
5. 미래에 2회 이상 나타난 ID만 골라 전체 실험을 진행하지 않는다. 미래 반복 여부로 표본을 선택하면 전체 대화형 서비스라는 목표와 달라진다.
6. 토큰 결측·비수치·음수 및 `Total tokens` 정합성을 점검한다. 문제 건수와 처리 규칙을 기록한다.
7. 기본 실험에서는 0토큰 기록을 유지하고 §5.1에 따라 별도로 표시한다. 긴 입력·긴 응답·토큰 극단값도 오류라는 근거 없이 삭제하거나 임의의 상한으로 줄이지 않는다. 대화형에는 완전 중복이 없으며, 같은 Timestamp의 서로 다른 요청은 모두 유지한다.
8. 새 요청이 없는 내부 빈 분은 연속 수집 가정 아래 요청 수·도착 기준 입력/최종 출력 합계를 0으로 집계한다. 완료 기준 출력은 별도로 집계하고, 이전 요청이 완료된 분의 값을 0으로 덮어쓰지 않는다. 빈 분을 삭제하지 않으며 실제 무요청과 수집 누락을 구분할 수 없음을 명시한다. 긴 공백을 사후에 골라 삭제하지 않는다.
9. 최대 과거창 60분을 확보하는 초기 준비 구간과 완전한 미래 10분을 구성할 수 없는 끝부분은 평가에서 제외한다. 첫·마지막 부분 관측 분도 표시하고 적격 시점 계산에 반영한다. 모든 모델에 같은 규칙을 적용한다.
10. 요청 도착이 없는 기간까지 실제 수집이 지속됐는지 확인할 수 없으므로, 관측 범위 밖으로 임의의 0 구간을 연장하지 않는다.
11. 응답시간 0초를 실패나 결측으로 단정하지 않는다. 기본 EDA에서 출력 토큰이 양수인 0초 기록이 확인됐으므로 유지한다. 원본 CSV는 덮어쓰지 않고 변환·집계·제외 이력을 별도 저장한다.

### 5.1 0토큰 기록을 남기고 구분하는 방법

**기본 결정은 ‘당장 삭제하지 않고, 다른 요청과 구분해 표시한다’이다.** 0토큰 기록의 원인이 실제 사용량 0인지, 오류 또는 기록 문제인지 현재 데이터만으로 확인되지 않았기 때문이다.

예를 들어 최근 15분에 요청 기록이 10건이고 그중 질문 길이가 0인 기록이 2건이라면, **‘전체 요청 수 10건’과 ‘그중 입력 0 요청 수 2건’을 함께 전달한다.** 입력 길이가 있는 요청은 8건이라는 구분 정보를 주는 것이다. 0인 기록을 없던 요청처럼 지우지 않고, 별도 숫자로 알려준다.

```text
zero_input_request_count_last_15min(t)
    = count(requests with t-900 <= a_i < t AND Request tokens_i == 0)
```

이 변수는 A/B/C 모두에 제공한다. 아직 미완료인 요청의 최종 출력이 0인지 확인해서 표시하지 않는다. 모델에 이 정보를 추가하는 것이 실제로 유용한지는 검증 대상이며, 0토큰 기록을 유지하는 편이 더 정확하다고 미리 결론 내리지 않는다.

주 실험 이후에는 **입력 토큰 0인 요청을 요청 수·대화 상태 계산에서 제외한 경우**를 별도 비교한다. 이때 다음 규칙을 지킨다.

- 제외 판정은 도착 시점에 알 수 있는 `Request tokens == 0`으로 한다. 현재 데이터에서는 이 1,856건이 사후에 확인한 입력·출력 모두 0인 기록과 일치한다.
- 원본, 예측 시점, 학습·평가 적격 시점, 두 목표값은 기본 실험과 동일하게 유지한다. 목표값은 항상 원래 대화형 요청 전체에서 계산한다.
- 요청 수에서 파생한 지연값·합계·변동성과 활동 대화 수·대화 상태만 입력 0 요청을 제외한 이력으로 다시 계산한다. 입력·완료 출력 합계, 입력 길이 분포, 모델 구성비, 별도 입력 0 요청 수 등 나머지 공통 특징은 기본 정의를 유지한다. 이는 기록 자체를 삭제하는 실험이 아니라 **요청·대화 활동으로 셀지의 영향**을 확인하는 비교이다.
- 포함·제외 설정별로 A/B/C를 같은 조건에서 비교한다. 어느 처리 규칙을 최종 채택할지는 검증 구간에서 결정하고, 최종 평가 결과를 본 뒤 유리한 규칙으로 바꾸지 않는다.

| 10분 | 76.69% |

모든 적격 시점에서 10분 요청 수·입력·최종 출력 합계가 원본 이벤트 합계와 일치했고, `[t,t+600)`의 양 끝 경계와 원본 해시 보존을 검증했다. 10분 출력 목표의 13.90%에는 구간 종료 시각 이상에 완료되는 응답이 포함되므로, §3.4의 정답 확정 조건은 그대로 필요하다. 이는 EDA 정답 구성 검증이며, 모델용 전체 특징과 학습·평가 표본 생성의 검증은 후속 구현에서 수행한다.

## 7. 모델 학습 및 평가

### 7.1 기본 구현

- 입력·출력 각각 A/B/C를 학습하여 총 6개 XGBoost 모델을 비교한다.
- 먼저 다음 10분 토큰 합계를 직접 예측한다. 요청 수와 평균 길이를 별도로 예측해 곱하는 구조는 기본 범위에서 제외한다.
- 목표별 공통 목적함수, 공통 탐색 범위와 튜닝 예산을 사용한다. 선택은 검증 성능으로 수행한다.
- 원래 토큰 단위의 합계를 직접 예측하며 음수 예측은 0으로 제한한다. 이 규칙을 모든 모델에 동일하게 적용한다.
- A/B/C 중 최종 채택 모델은 입력·출력별 검증 성능으로 각각 결정한다. 최종 평가 구간에서 가장 좋았던 모델을 사후 선택하지 않는다.
- 지수가중 평균·가중 활동 대화 수는 기본 실험 이후 선택적 비교로만 추가한다.

### 7.2 시간순 분할

대화형 관측 범위의 **시간 길이 기준**으로 앞 60%를 학습, 다음 20%를 검증, 마지막 20%를 평가에 사용한다. 요청 행을 무작위로 나누거나 요청 수 기준으로 기간 길이를 바꾸지 않는다. 정확한 시각 경계와 §3.4의 학습 정답 확정 규칙은 모델 성능을 보기 전에 저장한다. 내부 빈 구간은 현재 연속 수집 가정 아래 유지하며, 불연속 수집 근거가 추가로 확인되면 처리 이유와 변경 시점을 기록한다.

검증에서 특징·설정을 정하고 최종 평가 구간은 고정한다. 재학습을 수행한다면 재학습 시각과 사용 가능한 정답 표본을 기록한다. 동일한 목표의 A/B/C는 같은 학습 적격 시점과 평가 시점을 사용한다.

전체 기간의 기본 EDA와 10분 rolling target의 요약·5분과 10분의 비교를 설계 과정에서 확인한다는 점을 평가 한계로 명시한다. 마지막 20%가 설계 과정에서 전혀 보지 않은 데이터였다고 주장하지 않는다. 지금부터 이 구간의 모델 오차를 보고 변수·시간창·0토큰 처리·튜닝 설정을 선택하지 않는다.

평가 기간의 이미 관측된 요청을 이후 예측의 특징으로 사용하는 것은 허용한다. 평가 정답으로 모델·특징을 고르는 것은 허용하지 않는다. 두 기간에 걸쳐 지속되는 동일 대화의 과거 관측을 사용하는 것은 실제 운용과 일치한다.

### 7.3 단순 기준 예측

입력 토큰에는 직전 10분 합계 유지 예측을 포함한다. 전날 같은 구간 예측은 데이터가 충분히 연속적이고 과거 구간이 확보된 경우 추가한다.

출력 토큰에서는 직전 10분 도착 요청들의 최종합이 아직 확정되지 않을 수 있다. 따라서 완료 기준 최근 출력량 또는 예측 시점에 이미 확정된 과거 구간을 사용하는 기준을 명시한다. 완료 기준 값과 도착 기준 목표의 차이를 숨기지 않는다.

### 7.4 성능 지표와 해석

| 지표·결과 | 역할 |
|---|---|
| 입력·출력별 MAE | 주 평가 지표; 원래 토큰 단위 |
| 입력·출력별 RMSE | 큰 오차에 대한 보조 평가 |
| 목표값 0 구간·양수 구간별 오차 | 빈 수요를 잘 맞힌 효과와 실제 수요가 있는 구간의 성능을 구분 |
| B−A, C−B, C−A 개선폭 | 특징 묶음의 추가 가치 |
| 상대 일별·연속 기간별 오차 차이 | 개선의 일관성과 시기 의존성 |
| 높은 토큰 수요 구간 오차 | 큰 수요에서의 성능; 기준은 학습 자료에서 정함 |

0인 목표 구간이 있을 수 있으므로 MAPE를 주지표로 사용하지 않는다. 개선율 계산 시 기준 오차가 0이면 비율은 정의하지 않는다.

목표값 0·양수 구간은 **각 목표의 다음 10분 합계**로 구분한다. 1분 무요청 비율을 그대로 10분 정답의 0 비율로 사용하지 않는다. 높은 수요의 기준도 목표별 학습 자료에서 정해 검증·평가에 동일하게 적용한다.

1분마다 예측하는 10분 누적 목표는 서로 9분씩 겹친다. 각 시점에 10개 분별 예측을 내는 구조가 아니며, 분별 오차를 독립 표본으로 가정한 검정을 기본으로 사용하지 않는다. 상대 일별 짝지은 오차 차이를 보고하고, 가능하면 연속 시간 블록을 유지하는 bootstrap으로 개선폭의 불확실성을 제시한다. 블록 길이와 검정 방식은 평가 성능을 보고 선택하지 않는다.

입력과 출력의 결과는 별도로 판단한다. 성능이 좋아진 특정 구간만 골라 결론을 내리지 않는다. 지표가 엇갈리면 MAE를 우선하되 RMSE와 높은 수요 구간의 악화도 함께 보고한다.

위 차이는 각 원문의 방법론과 이번 연구 질문을 비교한 범위의 정리이다. 토큰 수요 예측 자체를 새로운 문제라고 주장하지 않으며, 대화 연결 정보의 추가 예측가치를 이번 프로젝트의 검증 대상으로 둔다.

### 8.2 이번 프로젝트의 기여 후보

> 집계 이력 기반 예측을 출발점으로, 최근 활동 대화 수와 대화별 관측 상태를 요약한 특징이 다음 10분 누적 입력·출력 토큰 예측에 추가 가치를 제공하는지 동일한 평가 조건에서 단계적으로 검증한다.

프로젝트의 차별성은 A/B/C 비교로 확인할 **대화 연결 정보의 추가 예측가치**에 있다. Session ID 사용, 입력·출력 분리, XGBoost 적용 자체를 최초의 기여로 주장하지 않는다.

원 논문과 목표·평가 기간·설정이 다르므로 ‘원 논문에 착안한 기준 모델 재구성’으로 표현한다. 원 논문의 수치와 직접 비교하여 우월성을 주장하지 않는다. 전체 관련 문헌에서 최초라는 주장에는 별도의 체계적인 문헌검토가 필요하다.

### 8.3 허용하는 결론의 범위

- 가능: 이 데이터·목표·평가 구간에서 C가 A보다 어느 정도 개선됐는지 설명.
- 가능: 입력과 출력, 평상시와 높은 수요 구간에서 효과가 달랐는지 설명.
- 가능: 충분한 집계 특징을 제공하면 대화 정보의 추가 효과가 작았다는 결과.
- 불가: 대화 상태가 수요를 유발하는 인과효과를 증명했다는 결론.
- 불가: 토큰 오차 개선만으로 GPU 비용·SLO·실제 처리량이 개선됐다는 결론.
- 불가: 다른 서비스·모델·지역에도 동일하게 일반화된다는 단정.

## 9. 수업 Proposal 구성

### 9.1 Problem statement

대화형 LLM 서비스에서 매 1분마다 다음 10분에 도착할 요청들의 입력·최종 출력 토큰 합계를 각각 예측한다. 이는 t+600의 단일 시점 값이나 10개 분별 값을 각각 예측하는 문제가 아니다. 과거 요청·토큰 이력에 최근 대화 상태를 추가했을 때 예측이 개선되는지 평가한다. 단기 수요 정보는 용량 계획의 기초가 될 수 있으나, 본 연구는 예측 성능 평가에 집중한다.

### 9.2 Dataset

공식 출처, 전체 원본 5,344,021행과 대화형 분석 표본 233,617행을 구분해서 제시한다. 대화형은 약 110일·55,920개 대화이며, 기본 EDA에서 확인한 ID 품질·반복 대화·빈 구간·0토큰 기록 통계를 함께 제시한다. 원자료는 요청 이벤트이며, 이를 1분 예측 시점과 다음 10분 누적 목표로 변환한다. 실제 달력 날짜는 제시하지 않는다.

### 9.3 Rationale and novelty

최근 수요의 지속성·변동성 및 대화 후속 요청의 시간적 관계를 분석할 수 있어 시계열 문제에 적합하다. 외부 변수나 뚜렷한 계절성의 존재를 전제할 필요는 없다. 기존 집계 예측을 기준으로 활동 대화 수와 상태 정보를 단계적으로 추가하여 효과를 분리하는 것이 이번 프로젝트의 차별점이다.

### 9.4 Proposal에서 결과를 설명하는 수준

실제 확인된 데이터 통계와 예비 EDA만 결과로 제시한다. 대화 정보의 성능 향상은 가설로 표현하고, 비교 방법·평가 기준·한계를 제시한다. 임의의 향상률을 약속하거나 아직 실행하지 않은 모델 결과를 작성하지 않는다.

## 12. 범위 밖의 작업과 변경 관리

다음은 기본 범위에 포함하지 않는다: 세션별 후속 확률 모델, 배경·세션 수요 분해, API 포함 전체 서비스 확장, 의미 정보 복원, GPU 시뮬레이션, 서버 배치·라우팅 최적화, 비용·SLO 평가, 확률 예측·경보 시스템 구축.

대화형 ID가 대부분 유효하지 않거나 반복 대화가 매우 적으면 데이터 적합성을 재검토한다. 이 경우 유리한 일부 표본만 사후 선택하지 않고, 대상 범위 변경 또는 가설의 한계를 문서화한다.

목표 구간, 분석 대상, 출력 정보의 이용 범위, 특징 묶음 또는 평가 규칙을 바꾸면 변경 이유와 시점을 기록한다. 이전 문서의 배경 수요 분해나 다중 지평 구상을 이번 설계에 자동으로 혼합하지 않는다.
