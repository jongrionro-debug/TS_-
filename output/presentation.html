발표의 핵심: 다음 10분의 입력·출력 토큰 합계를 예측합니다. 과거 요청·토큰 이력에 최근 활동 대화 수와 상태를 추가합니다. 이 정보가 예측을 개선하는지 확인합니다.

이 문서는 주제 선정 → 차별성 → 예측 문제 → A/B/C 입력 → EDA → 용어집 순서로 읽습니다. 발표할 때는 각 절의 발표 문장을 중심으로 설명하면 됩니다.

A

1. 왜 이 주제를 선택했는가?

출발점: 요청 건수만으로는 필요한 처리량을 설명하기 어렵다

요청이 같은 10건이어도 질문과 답변의 길이에 따라 처리해야 할 토큰 수가 달라집니다. 입력과 출력의 길이도 서로 다를 수 있습니다. 그래서 요청 건수와 함께 입력·출력 토큰 수요를 각각 예측합니다.

서비스 용량을 늘리는 데는 준비 시간이 필요합니다. 수요가 늘어난 뒤 대응하는 방식에는 지연이 생길 수 있습니다. 몇 분 뒤 수요를 미리 알면 용량 계획의 기초 정보로 쓸 수 있습니다. PreServe §5.2.1

왜 하필 대화 상태인가?

대화형 서비스에서는 한 번 질문한 대화에서 후속 질문이 들어옵니다. 같은 최근 요청 10건도 한 대화에서 나온 경우와 여러 대화에서 나온 경우의 다음 수요는 다를 가능성이 있습니다. 최근에 질문한 대화가 몇 개이고, 각 대화가 어느 상태인지가 추가 단서가 될 수 있다는 가설입니다.

선택 이유 실제로 확인한 근거 연구에서 확인할 점
시계열 문제에 적합 시간별 피크와 수요 규모 변화가 관측됨 최근 이력으로 다음 누적 수요를 예측
대화 연결 정보를 활용할 수 있음 대화 ID 55,920개, 반복 대화 비율 64.53% 집계 이력 이상의 정보가 있는지 비교
후속 요청이 짧은 간격에 나타남 관측된 후속 요청 쌍의 간격 중앙값 131초 최근 활동·상태를 단기 예측에 활용
토큰 길이가 일정하지 않음 입력 중앙값 517, 출력 중앙값 187토큰 입력·출력 목표를 따로 평가

무엇이 필요한가?

  • 데이터: 요청 시각, 대화 ID, 입력·출력 길이, 응답시간, 모델 종류가 필요합니다. BurstGPT_3에 이 정보가 있습니다.
  • 관측 규칙: 예측 당시 알 수 있었던 정보만 사용해야 합니다. 최종 출력 길이는 응답 완료 후에 사용합니다.
  • 비교 실험: 집계 이력이 충분한 A를 만들고, B와 C에 대화 정보를 단계적으로 추가해야 합니다.
  • 평가: 시간순 분할과 동일한 실험 조건으로 입력·출력 오차를 각각 비교해야 합니다.
발표 문장

“요청 수가 같아도 토큰 수는 다릅니다. 저희는 다음 10분의 입력·출력 수요를 예측합니다. 최근 대화의 활동과 상태가 추가 단서가 되는지 확인하려고 이 주제를 선택했습니다.”

근거: PRD §1·2, EDA 요약, Proposal 2·4·6쪽.

B

1. 노벨티는 정확히 어디에 있는가?

기여 후보는 대화 연결 정보의 추가 예측가치를 분리해서 검증하는 데 있습니다. A → B → C에서 모델 계열과 평가 조건을 맞추고, 입력 정보만 단계적으로 늘립니다.

선행연구 이미 수행한 일 이번 프로젝트가 추가로 묻는 질문
BurstGPT §5.4 집계 부하 이력·시간 정보를 XGBoost에 넣어 요청 수와 요청당 평균 토큰 수 예측 집계 특징에 대화 수·상태를 더하면 추가 이득이 있는가?
DynamoLLM §IV-B·D 과거 이력으로 부하 예측. 도착 요청의 출력 길이를 분류해 자원 구성·라우팅에 활용 대화 상태가 미래 누적 수요 예측에 더하는 정보는 무엇인가?
PreServe §4.1–4.3 과거 집계 토큰으로 10분 입력·출력 수요를 예측하고 개별 요청 부하 예측과 결합 대화 ID로 연결한 최근 상태를 추가하면 집계 예측을 개선하는가?
SageServe §6.4–6.5 ARIMA로 지역·모델별 다음 1시간 최대 TPS를 예측해 자원 할당에 활용 대화 상태를 활용한 10분 누적 입력·출력 예측에 이득이 있는가?

위 비교는 네 논문의 방법과 이번 설계를 대조한 범위입니다. 토큰 예측, 10분 지평, 입력·출력 분리, XGBoost, Session ID 사용 각각은 최초의 기여로 주장하지 않습니다.

비교 확인할 가설 해석
B 대 A H1: 활동 대화 수가 추가로 유용한가? “얼마나 많은 대화에서 최근 요청이 있었는가”의 가치
C 대 B H2: 상태 요약이 대화 수를 넘어 유용한가? “그 대화들이 어떤 상태인가”의 가치
C 대 A, 목표별 비교 H3: 전체 추가 효과가 입력·출력에서 다른가? 입력에서만 개선되는 결과도 가능
현재 주장할 수 있는 범위

EDA는 대화 정보를 실험할 근거를 보여 줍니다. 성능 향상은 아직 검증하지 않았습니다. C가 가장 좋다고 가정하지 않으며, 개선이 없는 결과도 보고합니다. 토큰 오차 개선과 GPU 비용·전력·지연 개선은 별도로 검증해야 합니다.

발표 문장: “집계 이력에 대화 연결 정보를 더하는 것이 유용한지 검증하는 연구입니다. A/B/C에 같은 모델과 평가 조건을 적용합니다.”

근거: PRD §4·7·8, Proposal 3·5·14쪽. 위 링크는 각 선행연구 원문입니다.

C

2. 시스템은 언제 무엇을 예측하는가?

한 행의 입력으로 두 누적 수요를 예측한다

항목 확정한 정의
대상 Log Type == "Conversation log"인 대화형 요청 전체
예측 시점 t 원본 상대 초의 60초 경계마다 1회
입력 X(t) t 이전에 알 수 있는 로그를 요약한 숫자 한 행
입력 목표 Y_input(t) [t, t+600초)에 도착한 요청들의 Request tokens 합계
출력 목표 Y_output(t) 같은 구간에 도착한 요청들의 최종 Response tokens 합계
예측 모델 A/B/C 각각 입력용·출력용 XGBoost 회귀 모델, 총 6개

다음 10분 누적값 한 쌍을 예측합니다. 예측 구간은 1분마다 이동하므로 이웃 구간끼리 9분이 겹칩니다. 10분 뒤 한 시점의 값이나 1분별 값 10개를 내는 구조와 구분합니다.

이 흐름은 입력 묶음의 포함 관계를 나타냅니다. A/B/C는 각각 학습합니다. A의 예측값을 B에 전달하거나, B의 예측값을 C에 전달하는 구조가 아닙니다.

출력 토큰은 언제 알 수 있는가?

요청 i의 도착시각을 a_i, 완료시각을 c_i로 둡니다. c_i = Timestamp_i + Elapsed time_i입니다.

정보 예측 입력으로 사용할 조건
요청 시각·대화 ID·입력 길이·모델 a_i < t
최종 출력 길이·최종 응답시간 c_i < t
미래 도착 요청의 입력·출력 예측 입력으로 사용하지 않음. 사후 정답 계산에만 사용

설명용 예시: 11:59에 입력 100토큰 요청이 도착하고 12:01에 출력 200토큰으로 끝납니다. 12:00 예측 입력에는 입력 100을 쓸 수 있습니다. 최종 출력 200은 아직 쓸 수 없습니다. 이 예시의 시각은 설명용이며 데이터에 실제 날짜를 부여한 것이 아닙니다.

목표 출력과 과거 출력 이력은 기준이 다릅니다. 목표는 앞으로 도착할 요청의 최종 출력 전체입니다. 과거 출력 특징은 이미 완료된 요청의 출력 전체를 완료시각에 합산합니다. 구간 안에서 실제로 생성된 토큰 수나 GPU 생성률을 측정하는 것이 아닙니다.

예를 들어 예측 구간 안에 도착해 구간이 끝난 뒤 완료된 요청도, 최종 출력 전체가 그 구간의 정답에 포함됩니다. 이후 처음 등장할 대화와 상태 추적 대상 밖의 대화도 정답에 포함합니다.

학습·평가 계획

관측 시간 길이의 앞 60%를 학습, 다음 20%를 검증, 마지막 20%를 평가에 사용합니다. 입력·출력 각각 검증 MAE로 A/B/C를 선택합니다. RMSE와 0·양수·높은 수요 구간 오차도 보고합니다.

학습 시각 T에는 t+600 ≤ T인 입력 정답만 사용합니다. 출력 정답은 그 구간의 모든 요청이 c_i < T로 완료돼야 합니다. A/B/C에는 동일 목표별 학습·평가 시점과 튜닝 예산을 적용합니다.

발표 문장: “매 1분마다 과거 로그를 숫자 한 행으로 요약합니다. 앞으로 10분에 들어올 요청의 입력 합과 최종 출력 합을 각각 예측합니다.”

근거: PRD §1.3·3·7, Proposal 5·8쪽.

D

2. A에는 정확히 어떤 입력을 넣는가?

A는 대화 ID로 요청을 연결하지 않고 계산할 수 있는 집계 기준 모델입니다. 아래 목록을 B/C에도 그대로 제공합니다. 여기서 ‘모델 입력’은 XGBoost의 설명변수이고, ‘입력 토큰’은 LLM에 제출된 요청 길이입니다.

첫 실험의 공통 입력 목록

입력 묶음 계산 대상 정확한 시간창·요약
수요 지연값 요청 수, 입력 토큰 합, 완료 기준 출력 토큰 합 각 통계의 직전 1·2·3분 값
누적 수요 같은 세 통계 각각 최근 5·15·30·60분 합계
수요 변동성 같은 세 통계의 분별 값 최근 15분 표준편차
요청당 입력 길이 분포 최근 15분에 도착한 요청들의 Request tokens 평균·표준편차·중앙값·90분위수

시간창을 말로 풀면

  • 직전 1분 값: [t-60, t)의 값입니다.
  • 직전 2분 값: [t-120, t-60)의 값입니다. 최근 2분 누적값과 다릅니다.
  • 직전 3분 값: [t-180, t-120)의 값입니다.
  • 최근 W분 합계: [t-W×60, t)의 합계입니다.
  • 요청 수·입력 길이는 도착시각, 완료 기준 출력 합계는 완료시각으로 시간창에 넣습니다.

표준편차는 모집단 기준 ddof=0을 사용합니다. 분위수는 선형 보간으로 계산합니다. 실제 날짜가 없으므로 요일·주말·공휴일은 입력에 넣지 않습니다.

완료된 요청도 없음 완료 기준 출력 합계는 0

입력 0 요청 수는 미래 출력 정보를 확인하지 않고 계산합니다. 0토큰 기록과 극단값은 기본 실험에서 유지합니다.

왜 A에도 입력 길이 통계를 주는가?

C에만 길이 정보를 주면, 성능 차이가 대화 연결 때문인지 단순한 길이 정보 추가 때문인지 구분하기 어렵습니다. 그래서 A에도 전체 최근 요청의 길이 분포를 제공합니다.

발표 문장: “A에는 요청·입력·완료 출력의 최근 이력과 누적량, 변동성을 넣습니다. 요청 길이 분포, 시간대, GPT-4 비율, 입력 0 요청 수도 넣습니다. B와 C도 이 정보를 똑같이 받습니다.”

근거: PRD §4.2·4.3·5.1. 이 목록은 첫 실험 설계이며, 전체 모델용 특징 행렬은 아직 구현 전입니다.

E

2. B와 C는 무엇을 추가하는가?

B = A + 활동 대화 수 3개

추가 입력 계산 규칙
최근 5분 활동 대화 수 [t-300, t)에 요청이 있었던 유효 Session ID의 고유 개수
최근 15분 활동 대화 수 [t-900, t)의 고유 유효 Session ID 수
최근 30분 활동 대화 수 [t-1800, t)의 고유 유효 Session ID 수

설명용 예시: 최근 5분의 요청 10건이 한 대화에서 나왔다면 요청 수는 10, 활동 대화 수는 1입니다. 서로 다른 10개 대화에서 나왔다면 요청 수와 활동 대화 수가 모두 10입니다.

활동 대화는 최근에 요청이 기록됐다는 뜻입니다. 실제로 창이 열려 있거나, 사용자가 질문을 작성 중이거나, 응답 생성이 진행 중임을 뜻하지 않습니다.

C = B + 최근 30분 활동 대화들의 상태 요약

먼저 최근 30분에 요청이 있었던 대화를 고릅니다. 대화마다 아래 상태를 계산한 뒤, 전체 활동 대화에 걸쳐 숫자로 요약합니다. 대화별 독립 모델을 만드는 방식이 아닙니다.

상태 대화별 계산 모델에 추가하는 요약
최근성 t − 마지막 과거 요청시각 중앙값·90분위수
관측 요청 횟수 파일 내 t 이전의 해당 대화 요청 수 중앙값·관측 요청이 1회인 대화 비율
관측 연령 t − 파일 내 최초 과거 요청시각 중앙값
마지막 입력 길이 해당 대화의 마지막 과거 요청 Request tokens 중앙값·90분위수
입력 길이 변화 마지막 입력 길이 − 직전 입력 길이 변화량 중앙값·계산 가능한 대화 수

30분은 요약할 대화를 고르는 기준입니다. 요청 횟수와 관측 연령은 최근 30분으로 자르지 않습니다. 선택된 대화의 파일 내 t 이전 이력 전체를 사용합니다. 마지막 두 입력도 그 과거 이력에서 찾습니다.

설명용 예시: 40분 전에 처음 요청했고 2분 전에 다시 요청한 대화는 최근 30분 활동 대화에 포함됩니다. 이 대화의 최근성은 2분, 관측 연령은 40분, 관측 요청 횟수는 2입니다. 두 입력 길이가 100과 300토큰이면 변화량은 +200입니다.

A의 길이 통계와 C의 길이 통계는 어떻게 다른가?

A는 최근 15분의 모든 요청에서 입력 길이 중앙값 등을 계산합니다. C는 활동 대화별로 마지막 요청 하나씩을 골라 길이를 요약합니다. 같은 대화가 여러 번 요청했어도 C의 마지막 길이 요약에는 한 번만 들어갑니다.

경계와 결측 처리

  • 활동 대화가 없으면 B의 세 개수는 0입니다. C의 변화량 계산 가능 대화 수도 0입니다.
  • 정의할 수 없는 중앙값·분위수·1회 대화 비율은 결측으로 둡니다. A/B/C에서 결측 행을 제각각 삭제하지 않습니다.
  • Session ID는 연결키로만 사용합니다. ID 문자열, 사용자 정보, 프롬프트 원문, 임베딩은 모델에 넣지 않습니다.
  • 전체 CSV에서 얻은 최종 대화 길이·최종 종료시각·미래 반복 여부는 입력으로 쓰지 않습니다.
  • 관측 연령은 기본 C에 포함합니다. 대화 내 과거 요청 간격은 이후 확장 실험입니다.

발표 문장: “B는 최근에 활동한 대화가 몇 개인지 추가합니다. C는 대화별 최근성, 요청 횟수, 관측 연령을 추가합니다. 마지막 질문 길이와 그 변화도 함께 요약합니다.”

근거: PRD §4.2–4.4, Proposal 5·8쪽. B의 활동 수 EDA는 실행됐으며, 기본 C 전체의 모델 입력 생성·효과 검증은 예정입니다.

4. 단어집 — 데이터와 시스템

표의 첫 열은 단어: 풀어쓴 단어 형식입니다. 약어는 영문 원어를, 일반 용어는 한국어 풀이를 적었습니다.

단어: 풀어쓴 단어 이 프로젝트에서의 의미
LLM: Large Language Model / 대규모 언어 모델 요청을 받아 텍스트를 생성하는 모델
Token: 토큰 / 모델이 텍스트를 처리하는 단위 글자 수·단어 수와 일대일로 같지 않음
Token demand: 토큰 수요 다음 구간에 도착할 요청들의 입력·최종 출력 합계
Forecasting: 미래 값 예측 과거에 관측 가능한 정보로 이후 수요를 추정
Request: 요청 서비스에 제출된 호출 한 건
Prompt: 모델에 전달하는 입력 내용 공개 로그에 원문은 없으며 길이만 활용
Response: 모델이 생성한 응답 공개 로그에서 최종 길이를 사용
Conversation: 대화 같은 Session ID로 연결된 요청 묶음
Session ID: Session Identifier / 대화 식별자 연결키. 사용자 ID나 예측 입력 문자열이 아님
UUID: Universally Unique Identifier / 범용 고유 식별자 대화 ID 형식 점검에 사용. 형식만으로 유효성 단정 불가
BurstGPT_3: 이번 실험에 사용하는 공개 로그 파일 전체 파일에서 Conversation log만 주 분석에 사용
API: Application Programming Interface / 프로그램 호출 인터페이스 API log는 이번 주 실험에서 제외
